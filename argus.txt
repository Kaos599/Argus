## TL;DR (read this first)

We have been manually doing one thing every day for months that *should* be a product:

> *"Give me stats on any new users from the last 15 hours — name, email, message count, personas they're talking to. Same for returning users. How many completed story onboarding."*

We built a digest endpoint in Blaze to formalize it. The endpoint works, but it is **static and situational** — every new question requires editing Python, adding fields to a Pydantic model, modifying a Slack formatter, redeploying. The thing we actually want — *"agent that reads our DB, decides what's interesting, renders cards we can drill into, and re-runs itself on a schedule"* — does not exist yet for MongoDB.

The Google Cloud **Rapid Agent Hackathon** runs through **June 11, 2026** (about 11 days from today) and has a **dedicated MongoDB partner track** that requires exactly what we'd want to build: a Gemini-powered agent that uses Google Cloud Agent Builder and integrates the MongoDB MCP server. ## Part 1 — The Lived Context: Why this idea exists

> **Frame for this section:** Blaze is the *case study* that grounds the pain — a real product whose daily operating loop revealed the gap this hackathon project fills. **None of Blaze's code, data, or schema crosses over into the hackathon build.** The hackathon repo is clean-room. What we carry forward is *the shape of the pain* and the *evidence* that this is a problem someone actually has — useful for the README's "Potential Impact" rubric item, and useful here to ground our design instincts in a real example rather than an imagined one.

### 1.1 The pattern we kept hitting (in Blaze)

Every couple of days, the same conversation:

- **Question:** "How many users signed up in the last 12 hours? Give me name, email, persona, message count."
- **The move:** Open Claude Code, MongoDB MCP is connected, write a one-off `db.users.find({...})` + `db.chats.aggregate([...])` chain against Blaze's prod MongoDB.
- **Output:** A markdown table pasted back into the conversation. Useful for that moment. Discarded after.

Then the question evolves: *"How many of them have actually completed story onboarding?"* Different query. *"Of returning users in the last 7 days, what's their warmth distribution?"* Different query. *"Of users who got the retention email yesterday, did any of them come back and message someone?"* Different query.

Each variant is a new conversation, a new ad-hoc query. We never accumulate the leverage of "the system already knows how to answer questions in this shape."

### 1.2 What we built (Blaze's digest endpoint) and why it's still painful

We formalized the most-asked variant into a real endpoint inside Blaze:

**File:** `~/Work/ai-persona-practice/backend/app/admin/router.py` (lines 436–442)

```python
@router.get("/analytics/daily-digest", response_model=DailyDigestResponse)
async def admin_daily_digest(
    x_admin_key: str | None = Header(default=None, alias="X-Admin-Key"),
) -> DailyDigestResponse:
    """Generate the 12-hourly signup + activity digest and post it to Slack."""
    _check_admin_key(x_admin_key)
    return await _build_daily_digest()
```

`_build_daily_digest()` runs **nine separate MongoDB queries** — a time-windowed `find` on `users`, a fan-out on `chats`, a `$group` aggregation for active users in the window, a `$addToSet` for persona breakdown, a sort for top streaks, etc. Result is serialized into a Pydantic `DailyDigestResponse` model with eight fixed fields, then formatted as a Slack message:

```
*Blaze 12h Digest — 2026-05-31*
_10:00 → 22:00 IST_

*📊 Overview*
• Total users:          *2,143*
• Active (12h):         *47*
• Returning (7d):       *12*
• New signups:          *3*
...

*🆕 New Signups (3)*
1. *Raj Kumar* `raj@example.com` — 14:32 IST | google | active | 2 chats
   › ishita · 12 msgs · active
   › aadya · 5 msgs · completed
```

It works. But to ask a *new* question — say, *"show me users with 5+ messages AND warmth ≥ 3 AND have completed story onboarding"* — we'd have to:

1. Write a new MongoDB aggregation.
2. Add a new field to `DailyDigestResponse`.
3. Update the Slack formatter.
4. Deploy the backend.

That is the "static and situational" bottleneck. Every new question becomes a one-week PR. The endpoint shape is wrong, not the implementation — no amount of "add more fields" makes it more flexible; each field we add narrows what the endpoint is *for*.

### 1.3 Why a rich schema doesn't save you — it makes it worse

The thing that should make Blaze tractable — its rich, well-typed schema — is the same thing that makes the digest endpoint fragile. There's too much there to commit to fixed fields. Quick tour of what we'd want to be able to query *dynamically*:

**Per-user lifecycle** (`backend/app/models/user.py`):
```python
class CumulativeMetrics(BaseModel):
    total_messages_sent: int = 0
    total_messages_received: int = 0
    total_reactions_given: int = 0
    total_reactions_received: int = 0
    total_prompt_tokens: int = 0
    total_completion_tokens: int = 0
    total_cost_usd: float = 0.0
    total_chats: int = 0

class SubscriptionState(BaseModel):
    status: SubscriptionStatus = "trial_pending"
    trial_starts_at: datetime | None = None
    trial_ends_at: datetime | None = None
    current_period_end: datetime | None = None
    ...
```

**Per-chat warmth + persona state** (`backend/app/models/chat.py`):
```python
class ConversationState(BaseModel):
    mode: Literal["simulation", "open_chat"] = "simulation"
    warmth: float = 0.0
    effective_warmth: float = 0.0
    interest_ledger: list[dict] = Field(default_factory=list)
    is_in_doubt: bool = False
    current_turn: int = 0
    persona_scratchpad: dict = Field(default_factory=dict)
    last_compact_turn: int = 0
```

**Per-message warmth deltas + coaching labels:**
```python
class MessageDocument(BaseModel):
    role: Literal["user", "assistant"]
    warmth_at_send: float = 0.0
    warmth_delta: float = 0.0
    coaching_label: Optional[str] = None  # "Crushing it 🔥" etc
    event_type: Literal["message", "no_response", "blocked", "unsend", ...]
    user_reaction: Optional[str] = None
    ai_reaction: Optional[str] = None
```

Every one of these fields is a *latent insight axis*. We could be asking:

- *"Which coaching labels precede the biggest warmth gains?"*
- *"What's the message-count distribution for trial users at hour 24, 48, 72?"*
- *"For users who hit warmth ≥ 4 in their first session, how many converted to paid?"*
- *"Which personas have the highest `consecutive_no_response_count` ceilings before user abandonment?"*

We *can't* — not without writing more endpoints. And every endpoint is locked-in by the time we deploy. **The insight is hiding in the schema; the endpoint shape can't reach it.** This is the universal problem the hackathon project solves — any product with a rich MongoDB schema has the same dynamic between "what's in the data" and "what your dashboard can ask."

### 1.4 The Blaze Eval skill is the same problem at a smaller scale

We even built a *whole Claude Code skill* (`~/.claude/skills/blaze-eval/SKILL.md`) to encode the canonical diagnostic queries — e.g., compactor health, warmth progression, response-type breakdown:

```javascript
// All traces for this chat, chronological
db.traces.find({ "context.chat_short_id": "CHAT_SHORT_ID" }).sort({ timestamp: 1 })

// Response type breakdown
db.traces.aggregate([
  { $match: { "context.chat_short_id": "CHAT_SHORT_ID", type: "chat_send" } },
  { $unwind: "$events" },
  { $match: { "events.event": "chat.llm.response" } },
  { $group: { _id: "$events.data.response_type", count: { $sum: 1 } } }
])
```

The skill is genuinely useful. But it's still a *manual* diagnostic surface — the evaluator has to know which query to run for which symptom. Same root problem: the system doesn't *propose* what to look at; the human does.

### 1.5 What "dynamic" should actually mean

The thing we keep gesturing at is not "a chatbot for your database." It's a system where:

1. The agent **owns the question-generation step**, not just the answering step.
2. The agent **looks at the schema** and **picks what's interesting** without being told.
3. The output is **opinionated, compact insight cards** — not a chat thread, not a static dashboard, not a CSV.
4. The cards **update themselves** on a cadence and **propose drill-downs** ("you have 12 users in this segment — open this for the list?").
5. The dashboard is **generative** — Gemini decides the card layout because we can't predict what insights will exist.

That is the project. Blaze is the case study that proves the pain is real; the hackathon product generalizes the pattern to **any** MongoDB. Blaze's codebase, data, and schema **do not** carry over — they only inform our design intuitions.

### 1.6 Concrete Blaze-shaped use cases (illustrative; demo will run on synthetic data)

These are the kinds of questions the agent should be able to ask itself when pointed at a Blaze-like database. Listed here to make the pain concrete, not because we'll use Blaze data:

| Use case | What the agent does | Card output |
|---|---|---|
| **"Show me retention email impact"** | Joins `users.created_at` × `users.last_login` × email-event timestamps; computes "users who logged in within 24h of email open" cohort | Card: bar chart of cohort sizes per email template + click-through to the user list |
| **"How is story onboarding working?"** | Detects onboarding-completion flag in user docs; computes funnel from signup → onboarding-start → onboarding-complete → first-message; flags the biggest drop | Card: waterfall + the actual user IDs at each drop |
| **"What's killing warmth?"** | Groups `messages` by `coaching_label`; ranks labels by avg `warmth_delta`; finds the labels with the most negative deltas | Card: ranked list of "warmth-killer" labels with example messages |
| **"What's the trial → paid conversion looking like?"** | Joins `users.subscription` to `chats.metrics.message_count_user`; segments by "messages in first 24h"; computes conversion rate per segment | Card: cohort grid + dollar-value-at-stake |
| **"Persona popularity drift"** | Time-series of new chats per persona, week-over-week, with statistical change-point detection | Card: small-multiple sparklines, biggest-mover called out |

All of these are queries we've literally written ad-hoc in Claude Code at some point. The hackathon project would surface them automatically — for Blaze-the-database, but more importantly, for *any* database with similar shape (which is most consumer apps).

## Part 3 — Google Cloud Agent Builder in 2026: what's actually shipping

### 3.1 The naming is genuinely confusing — here's the actual hierarchy

At Google Cloud Next 2026, Google **renamed Vertex AI to Gemini Enterprise Agent Platform (GEAP)** and folded Agentspace into it. The current hierarchy:

- **Gemini Enterprise Agent Platform (GEAP)** — umbrella (formerly "Vertex AI")
  - **Agent Studio** — low-code visual canvas (formerly Vertex AI Agent Builder / App Builder)
  - **Agent Development Kit (ADK)** — open-source code-first framework (Python, TypeScript, Go, Java)
  - **Agent Garden** — prebuilt agent templates
  - **Agent Runtime** — managed serving (formerly Vertex AI Agent Engine, now called "Deployments" in console)
  - **Model Garden** — 200+ models
  - **Memory Bank** — long-term agent memory

**What the Devpost rules mean by "Google Cloud Agent Builder":** anything in this family qualifies — Agent Studio (no-code) or ADK (code-first). For a hackathon judged 25% on Technological Implementation, **ADK is the right pick.** Agent Studio alone gives the judges nothing to evaluate; ADK lets us write real Python they can review.

### 3.2 MCP is first-class in ADK — this is the killer feature for us

`McpToolset` is a built-in ADK primitive. Drop the MongoDB MCP server in as a stdio subprocess, ADK auto-discovers the tools and proxies them to the agent. Three transports supported: stdio (local subprocess), Streamable HTTP, SSE.

Canonical wiring (from the official `google/adk-docs` repo):

```python
from google.adk.agents import Agent
from google.adk.tools.mcp_tool import McpToolset
from google.adk.tools.mcp_tool.mcp_session_manager import StdioConnectionParams
from mcp import StdioServerParameters

root_agent = Agent(
    model="gemini-flash-latest",   # resolves to gemini-3-flash-preview
    name="mongodb_agent",
    instruction="Help users query and analyze MongoDB collections",
    tools=[McpToolset(
        connection_params=StdioConnectionParams(
            server_params=StdioServerParameters(
                command="npx",
                args=["-y", "mongodb-mcp-server", "--readOnly"],
                env={"MDB_MCP_CONNECTION_STRING": "mongodb+srv://..."},
            ),
            timeout=30,
        ),
    )],
)
```

That's 15 lines and we have an agent that can `find`, `aggregate`, inspect schema, etc. on the user's database. The rest of the project — insight selection, card rendering, scheduling — is the part where we earn the prize.

## Part 4 — MongoDB MCP: tools, safety, what's NOT in the box

### 4.1 What the server gives us

The canonical implementation is [`mongodb-js/mongodb-mcp-server`](https://github.com/mongodb-js/mongodb-mcp-server), shipped by MongoDB Inc. TypeScript/Node, distributed via `npx`, Docker, and bundled into the official Claude/Codex/Cursor plugins. Two transports: stdio (default, for local agent integration) and Streamable HTTP (explicitly NOT recommended for production without an auth gateway in front).

**Tools provided** — 24 database + 13 Atlas:

| Category | Tools |
|---|---|
| **Read** | `find`, `aggregate`, `aggregate-db`, `count`, `explain`, `export` |
| **Metadata** | `list-databases`, `list-collections`, `collection-indexes`, `collection-schema`, `collection-storage-size`, `db-stats`, `mongodb-logs` |
| **Connect** | `connect` |
| **Write (disabled in `--readOnly`)** | `insert-one/many`, `update-one/many`, `delete-one/many`, `create-index`, `drop-index`, `rename-collection`, `drop-collection`, `drop-database` |
| **Atlas mgmt (separate auth)** | `atlas-list-orgs/projects/clusters/db-users/alerts`, `atlas-inspect-cluster/access-list`, `atlas-create-free-cluster/project/db-user/access-list`, `atlas-connect-cluster`, `atlas-upgrade-cluster`, `atlas-get-performance-advisor` |

This session's deferred-tool list (`mcp__MongoDB__aggregate`, `mcp__MongoDB__find`, `mcp__MongoDB__collection-schema`, etc.) is the read-only subset — consistent with running in `--readOnly` mode.

### 4.2 The safety model — the most important part for our product

We will be asking users to **paste a connection string to their production database**. We have to think about this like building a banking app, not a hackathon toy. MongoDB's official Security Best Practices doc is unambiguous and we should follow it verbatim:

1. **`--readOnly` flag always on.** When set, write tools are *removed from the tool list* — not just refused. Defense layer 1.
2. **Use a read-only DB user too.** Don't trust the flag alone. Defense layer 2.
3. **Never put credentials in CLI args** (they show up in process lists). Use `MDB_MCP_CONNECTION_STRING` env var.
4. **For HTTP transport** (if we ever expose one), put it behind an OAuth 2.1 resource server / reverse proxy. Anti-patterns: direct auth, pass-through auth.
5. **`disabledTools` config** to disable Atlas-management tools we don't need.
6. **Per-tool user confirmation** for dangerous ops (most are gone in readOnly anyway).

**Our implementation pattern:** spawn `mongodb-mcp-server@latest --readOnly` as a **subprocess per authenticated user request**, with their connection string injected via env var. Don't pool servers across tenants. One subprocess per user request, killed when the request ends.

### 4.3 Multi-tenancy — we own it, MCP doesn't

The MCP server has **no notion of tenants**. MongoDB's hands-on guide lists three patterns we'd inherit:

- **Database-per-tenant** — one Atlas DB per customer; strongest isolation; config sprawl.
- **Collection-per-tenant** — shared DB with prefixed collections.
- **Shared collections with `tenantId` field** — every query must filter; cross-leak risk if the LLM forgets the filter (and it will).

For our hackathon, the subprocess-per-request pattern (per 4.2) handles isolation cleanly — we never read or write our own data, just proxy queries against the user's DB. If we ever cache schema or insight history, that goes in *our* Atlas with a `tenantId` field — and that's *our* multi-tenancy concern, not the user's database's.

### 4.4 Schema inference — what `collection-schema` actually does

Under the hood, the official MCP server uses the [`mongodb-js/mongodb-schema`](https://github.com/mongodb-js/mongodb-schema) library. It:

- **Samples ~100 documents by default** (configurable).
- Recursively descends nested docs (`subFields`).
- Marks a field "required" if it appears in 100% of sampled docs (probabilistic, not authoritative).
- Handles inconsistent types as union types (`"string|null"`).
- Returns indexes alongside schema.

**Gotcha:** sampling 100 docs out of millions misses rare-but-important fields. E.g., `subscription.canceled_at` only exists on 0.5% of users → 99.5% chance a 100-doc sample misses it entirely. Our agent will need to **probe with `{$exists: true}` aggregations** on candidate fields after initial schema sampling. This is a real implementation detail to design for, not a rounding error.

### 4.5 Vector search via MCP — yes, with caveats

`$vectorSearch` is supported as the first stage of an aggregation pipeline. The agent can create vector indexes, `insert-many` with automatic embedding (requires `MDB_MCP_VOYAGE_API_KEY`), and run semantic queries. Pre-filtering on vector index fields was added in Oct 2025. **Quantization is NOT supported via MCP** — limiting for very high-dim embeddings.

For our hackathon: we use vector search if we need to find "similar users" or "similar conversations" for an insight ("here are 5 other users who hit the same warmth pattern as this one"). Free Atlas tier supports vector indexes — no extra cost.

### 4.6 What MCP does NOT give us — gaps we'd have to build around

- **No scheduling/cron.** MCP is request-response. The cron tick has to live in our backend (Cloud Run + Cloud Scheduler, or a small Python loop) and call MCP tools each tick.
- **No change streams via MCP.** MongoDB's [Real-Time Customer Retention reference architecture](https://www.mongodb.com/docs/atlas/architecture/current/solutions-library/customer-retention/) uses Atlas Stream Processing + change streams *natively*, not via MCP. If we want sub-minute reaction to DB writes, MCP polling is the wrong tool — we'd want change streams directly. **For the hackathon, MCP polling on a 5-minute tick is fine.** Change streams are a v2 story.
- **No semantic layer / cached "what does this collection mean."** Every session re-samples. We memoize schema + LLM-derived semantics ourselves in our own Atlas DB.
- **No multi-tenant authz.** §4.3.

## Part 5 — The hard problem: schema → insights (where we differentiate, where we don't)

This is the part that will make or break the project. The agent has to **decide what's interesting** without being told. That problem is *partially* solved in adjacent spaces and we need to be honest about where.

### 5.1 The crowded spaces — don't pitch as these

- **Text-to-SQL / text-to-MQL.** Solved-ish for SQL by [Vanna AI 2.0](https://github.com/vanna-ai/vanna), Hex Magic, DataChat. Vanna's accuracy paper shows schema-only prompting hits ~3% accuracy; RAG-over-examples lifts it to ~80%. **But Vanna doesn't support MongoDB.** Their DB list is Snowflake/BigQuery/Postgres/MySQL/etc. No Vanna-for-Mongo. That's a real, narrow gap.
- **Auto-insight engines on warehouses.** [Power BI Quick Insights](https://learn.microsoft.com/en-us/power-bi/create-reports/insights), [Tableau Explain Data](https://help.tableau.com/current/online/en-us/explain_data_explained.htm), [ThoughtSpot SpotIQ](https://docs.thoughtspot.com/cloud/latest/spotiq-custom) all have multi-year head starts on the statistical rigor (Seasonal Hybrid ESD for anomaly detection, ridge-regression-based dimension explanation, change-point algorithms). We can't out-engineer them on time-series statistics in 11 days. But they all assume a *relational warehouse* with a defined semantic layer. None of them point at a raw MongoDB and say "go."
- **Product-analytics agents.** [Amplitude Global Agent](https://amplitude.com/ai-agents), [Mixpanel Agent](https://docs.mixpanel.com/docs/mixpanel-agent), [Heap Sense](https://www.heap.io/platform/artificial-intelligence). These do auto-insight chat-style. **But they all require your product to be instrumented in their taxonomy** (events → properties → users). They can't read an arbitrary user's MongoDB.

### 5.2 The whitespace — what we should pitch as

| Whitespace | Why it exists | Why we can hit it in 11 days |
|---|---|---|
| **MongoDB-native, schema-blind auto-insight** | No Vanna-for-Mongo. Incumbents assume warehouses or product-event taxonomies. | MongoDB MCP server is shipped; ADK gives us the agent loop for free. |
| **Insight CARDS instead of chat threads** | Mixpanel/Amplitude give chat answers. PowerBI/Tableau give static dashboards. Nothing renders compact, opinionated, drill-downable cards generated on the fly. | Tambo (gen-UI lib, §6) makes this a 2-day build. |
| **Cross-source closed-loop** ("email open → DB check → card update") | Production analog (MongoDB Atlas Stream Processing) requires the streaming infrastructure. A *polled* version via MCP is genuinely novel. | A cron tick + MCP polling is enough for the demo. |

**Pitch line:** *"MongoDB-native, schema-blind, generative insight cards — for the solo founder who doesn't have a data team."*

### 5.3 Academic prior art worth name-dropping in the README (not in the pitch)

Five 2025 papers converge on the multi-agent + skill-library + insight-scoring pattern:

- **DeepAnalyze-8B** ([arXiv 2510.16872](https://arxiv.org/html/2510.16872)) — first 8B agentic LLM trained end-to-end for data science.
- **AgentAda** ([arXiv 2504.07421](https://arxiv.org/html/2504.07421)) — "skill-informed" agent that pulls from a library of analytical methods via hybrid RAG matcher. Best-of-judge wins ~60% vs unskilled.
- **Data-to-Dashboard (KDD 2025)** ([arXiv 2505.23695](https://arxiv.org/pdf/2505.23695)) — multi-agent (domain detector → concept extractor → analysis generator → tree-of-thought chart picker).
- **MDSF** ([arXiv 2501.01014](https://arxiv.org/pdf/2501.01014)) — Multidimensional Data Storytelling Framework with insight scoring + Top-K ranking.
- **MaRGen** ([arXiv 2508.01370](https://arxiv.org/pdf/2508.01370)) — Amazon multi-agent that generates 6-page market reports in 7 min for ~$1.

**Borrow from these:** the "skill-library" framing (AgentAda) and the "insight scoring + Top-K ranking" mechanism (MDSF) are directly applicable.

### 5.4 The five insight categories the agent should auto-surface

Grounded in (a) the SpotIQ/Tableau/PowerBI feature sets, (b) the MongoDB customer-retention reference arch, (c) the MDSF insight-scoring taxonomy:

1. **Funnel breaks** — detect step-to-step drop ratios in any sequential collection. Auto-rank by `drop_ratio × volume_at_step` (absolute lost users, not just %). **Card UX:** waterfall + delta vs last period + suggested cohort to investigate.
2. **Cohort retention curves with cliff detection** — month-0-to-month-N retention matrix per signup cohort. Auto-flag the first "cliff." **Card UX:** heatmap + annotation arrow at cliff + suggested re-engagement segment.
3. **RFM segmentation with revenue-at-stake** — Recency / Frequency / Monetary → Champions / Loyal / At-Risk / Cannot-Lose-Them / Hibernating labels. Compute revenue-at-stake per segment so the card answers "who do I email tomorrow?" not "tell me about my customers." **Card UX:** 6-cell grid, each cell = count + dollar value + 1-click action.
4. **Channel/source attribution to LTV** — group new users by acquisition source, compute downstream LTV. This is the closest analog to your "email open → DB check → channel insight" story. **Card UX:** stacked bar with two metrics (volume vs LTV) + ratio callout.
5. **Behavioral anomaly / change-point on key metrics** — Seasonal Hybrid ESD or z-score-based change detection on any time-series the schema reveals. When a change fires, run the Tableau Explain Data pattern: schema-walk categorical fields, group time-series by each, score which grouping best "explains" the anomaly. **Card UX:** line chart with anomaly highlighted + top-3 dimensions explaining it ("Spike was driven by `utm_source=tiktok`").

**Optional 6th (stretch):** "Real-time behavioral signal" cards (`high-intent`, `exit-risk`, `search-friction`) patterned after the MongoDB customer-retention reference. Requires change-stream ingestion, not pure MCP — flag as v2.

### 5.5 The hidden hard problem: insight *selection*

When the agent CAN ask anything, how does it prioritize what to surface? Open techniques (combine, don't pick one):

- **MDSF insight scoring** — score each candidate insight on novelty, magnitude, actionability; show Top-K.
- **User-stated "north star"** — the onboarding flow asks "what do you care about most?" (revenue, retention, engagement); we weight insights toward that axis.
- **Anti-staleness** — don't show the same insight twice in a row unless it's changed by ≥X%.

This is the part of the project worth our best thinking. The UI is the demo; the insight selection is the moat.

## Part 6 — Generative UI: the differentiator, the library choice, the security model

### 6.1 Why generative UI matters here

If we render fixed templates (a `MetricCard` component, a `ChartCard` component, etc.), we're back to the Blaze digest problem at a different layer — *we* decide what shapes exist, and any insight that doesn't fit a template doesn't render. Generative UI flips this: the agent emits **typed component descriptions** (not raw JSX — see §6.3), and the frontend assembles them dynamically. New insight shapes show up without us shipping code.

This is also our judging-rubric weapon. Most submissions will be chat-only. Cards rendered on the fly will visibly stand out for **Design** (25%) and **Quality of Idea** (25%).

### 6.2 The library landscape (May 2026) and our pick

| Library | Type | MCP-native? | Fit for cards |
|---|---|---|---|
| **Tambo** ([tambo.co](https://tambo.co/)) | React SDK for "agents that speak your UI" | Yes (`MCPTransport`) | **★ Recommended** — exactly maps to our use case (Generative cards + Interactable boards) |
| **Vercel AI SDK UI + AI Elements** | Chat shell + shadcn primitives | Indirect | Best for the chat surface, not the cards |
| **Vercel `json-render`** | Catalog-based JSON → component, multi-framework | Via `@json-render/mcp` | Strongest security; newer (Mar 2026), less battle-tested |
| **assistant-ui** | Tool-call-driven generative UI | Yes | Solid; smaller community |
| **Vercel AI SDK RSC `streamUI`** | React Server Components | No | **Don't use** — Vercel's own docs mark it experimental and recommend AI SDK UI instead |

**Our pick:** **Tambo for the insight cards**, **AI Elements (shadcn) for the chat shell**, **shadcn/ui Recharts** as the underlying chart primitives Tambo registers. Tambo hit 1.0 in 2026, is open-source + self-hostable, registers components with **Zod schemas** (the agent picks which to render and streams props), and has first-class MCP support. The Generative / Interactable component split maps exactly onto our pattern: insight cards = Generative, the board they pin to = Interactable.

### 6.3 The chart-from-data-shape problem

When the agent has a result set, which chart does it pick? Don't reinvent — encode the [`ggauto`](https://github.com/nrennie/ggauto) decision table directly in the agent's prompt:

| Var 1 | Var 2 | Var 3 | Chart |
|---|---|---|---|
| date | continuous | — | line |
| continuous | continuous | — | scatter |
| discrete | continuous | — | bar |
| discrete | discrete | — | heatmap |
| date | continuous | discrete | small multiples |
| ... | ... | ... | ... |

Don't ship a full Draco / VizML solver — overkill for 11 days. shadcn/ui's chart primitives on Recharts v3 cover everything we need.

### 6.4 Security — Gemini emitting UI

If we're not careful, generative UI is an XSS vector. Three layers of defense:

1. **Never let the model emit raw JSX/HTML.** Tambo and json-render both enforce this *by design* via component catalogs + Zod schema validation. The model emits *data*, not markup.
2. **For any markdown the model does emit** (titles, narrative blurbs), use [`harden-react-markdown`](https://github.com/vercel/harden-react-markdown) (Vercel-maintained) or [`llmrender`](https://github.com/franciscop/llmrender). URL allowlist (`http:`/`https:` only; anything else becomes `#`), HTML-tag allowlist, `on*` event handlers always stripped.
3. **For URLs in tool args** (model might emit `<Card href="javascript:..."/>`), apply explicit URL transform with a two-gate sanitizer.

This is solved territory. We just have to use the libraries correctly.

### 7.4 The iterative-preview onboarding flow (locked decision)

This is the key UX pattern for the horizontal pitch. It's what gives the agent enough context to surface meaningful insights without forcing the user to fill in a wizard, and it's the single most demo-able sequence we can show in the 3-min video.

**Five steps, ~60 seconds total in the demo:**

1. **Connection step (~5 sec)** — User pastes their MongoDB connection string. Optionally: paste a URL to their product (the agent fetches og:description and h1 text as a *weak* hint about the domain). One free-text field: *"In one line, what does this product do?"* — optional, skipable.
2. **Schema sampling (~10 sec, animated)** — Agent calls MCP: `list-collections` → `collection-schema` (samples ~100 docs each) → targeted `{$exists}` probes on candidate fields the schema returned as "sometimes present." UI shows live ticker: *"Inspecting `users` … 7 fields with rich nesting"*, *"Inspecting `orders` … 3 time-series patterns detected"*. This is *fast theater* — feels like the agent is genuinely exploring.
3. **Hypothesis generation (~15 sec)** — Agent forms 2-3 candidate insight directions, each as a small **preview card** showing the *shape* of what the dashboard would look like (placeholder numbers, real chart type, real field names from the user's schema). Examples on a typical app DB:
    - *"User activation funnel — looks like there's a drop between signup and first action. Want me to dig in?"* (preview: small waterfall)
    - *"Retention cliff — your cohort retention drops sharply around day 7. Want me to find what's different about users who stay?"* (preview: heatmap)
    - *"Source-to-LTV mismatch — your highest-volume channel isn't your highest-value. Want me to surface which is which?"* (preview: stacked bar)
4. **User thumbs-up (~5 sec)** — User picks 1+ direction(s). Could be all three. UI is one-click per card: thumbs up = keep, thumbs down = never show this again, "more like this" = expand a category. This is the *teaching signal* the agent uses to weight future insight selection.
5. **Dashboard materializes (~25 sec, animated)** — Agent runs the actual queries against the live DB, Tambo cards stream in progressively (props start appearing before the data is fully computed, thanks to Gemini 3 streaming function calling). Cards land sorted by user's stated picks first, then the agent's own ranking.

**After onboarding (the always-on loop):**

- Cron tick every N minutes re-runs the picked insight modules and refreshes their cards.
- Every K ticks, the agent runs a *discovery pass*: samples new schema-blind hypotheses; if any score above a threshold (MDSF-style), surfaces them as a "Discover" card alongside the existing dashboard. User can thumbs-up to add to the always-on set or dismiss.
- The agent's "skill library" (AgentAda pattern) grows over time — modules the user keeps see their priors strengthened; modules the user dismisses get suppressed.

**Why this beats the alternatives:**

- vs *pure schema-blind* — the user-stated north star (even just from picking 1 of 3 cards) gives the insight scorer enough to avoid randomness.
- vs *heavy wizard* — the perceived friction is ~30 seconds of agent showing-off, not 5 minutes of form-filling.
- vs *non-iterative single-pass* — every cron tick the agent gets smarter about what *this* user values, without ever asking again.

**Demo storyboard implication:** the 3-min video opens on step 1 (connection paste), spends 60 sec showing steps 2-5 with live narration ("watch — it's just looking at the schema, it hasn't seen anything like this before"), then 90 sec on the actual cards (one detailed drill-down + one "and 4 more"), then 30 sec on cron refresh + new insight discovery the next "morning."
