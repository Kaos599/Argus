## What is Argus?

Argus is an agentic analyst for MongoDB Atlas. You paste a connection string. It samples the schema, generates a draft dashboard of insights, and lets you chat with your data. Every operation is read-only. The agent renders the right visualization as a card — charts, tables, summaries, anomalies — based on what you ask.

Argus is built for the people who look at a MongoDB cluster and want answers, not dashboards. The startup founder checking weekly retention. The product manager tracking funnel drop-off. The data engineer looking for anomalies in event volume.

## What Argus is not

- **Not a general-purpose chatbot.** Argus is specifically for MongoDB Atlas.
- **Not a write tool.** Argus is read-only by design. Three layers of write protection.
- **Not a hosted SaaS.** Argus is a self-hosted open-source project. You bring your own MongoDB.

## Read-only by default (the 3 layers)

The most important thing to know about Argus. We take write protection seriously.

1. **Layer 1: Read-only mode in the MCP server.** The `mongodb-mcp-server` runs with `MDB_MCP_READ_ONLY=true`. This strips every write tool from the registered tool list.
2. **Layer 2: Read-only database user.** During onboarding, we recommend creating a read-only user (e.g., `readAnyDatabase` role). Argus shows the exact MongoDB shell commands to create the right user.
3. **Layer 3: Planner-layer enforcement.** Even if a malicious prompt injection slipped through, the `argus-result-set-guard` blocks `$out` and `$merge` aggregation stages at compile time, before they reach MongoDB.

Watch the [3-min video](https://youtu.be/...) at 0:45 to see what happens when you ask Argus to "drop the users collection."

## 5-step onboarding (2-3 minutes from paste to first dashboard)

1. **Connect.** Paste a MongoDB connection string. Argus probes the cluster for reachability.
2. **Sample.** Argus enumerates collections, picks the top 5 by size, and samples 100 documents from each.
3. **Plan.** The planner LLM reads the schema and proposes a draft dashboard of insights.
4. **Render.** Argus generates the cards. You accept the ones you like and customize the rest.
5. **Refine.** You can drag-and-drop cards, resize them, and pin them to a watchlist. The layout persists.

The 2-3 minute budget (not "60 seconds" — we tried):

- Connection probe: 2-3 seconds
- Collection enumeration: 1-2 seconds
- Schema sampling (5 collections × 100 docs): 5-10 seconds
- Planner LLM call: 5-15 seconds
- Dashboard generation: 10-20 seconds
- User review time: 60-120 seconds (the human is the bottleneck)

## The 5 insight modules

Each module is generated by the planner based on the schema, then run as a MongoDB aggregation. The user can ask for any of them in the chat, or accept the planner's default.

| Module | What it does | MQL operators |
|---|---|---|
| **Funnel** | Conversion rates between top events. | `$group`, `$facet` |
| **Cohort** | Weekly retention by acquisition week. | `$group`, `$dateTrunc`, `$lookup` |
| **RFM** | Recency-Frequency-Monetary segmentation, 5×5 grid. | `$bucket`, `$densify` |
| **Attribution** | First-touch attribution. (Markov + Shapley in v2.) | `$group`, `$arrayToObject` |
| **Anomaly** | Z-score on daily metrics vs trailing 28-day mean. | `$setWindowFields`, `$stdDevPop` |

See [docs/example-pipelines.md](docs/example-pipelines.md) for the actual MongoDB Aggregation Pipeline code for each module.

## How we built it

[3-box architecture diagram, Mermaid source in `research/08-x15-architecture-diagram.md`]

### The 3 tiers

- **Vercel** hosts the Next.js 15 frontend, with the Tambo React SDK for generative UI.
- **Cloud Run** hosts the self-hosted Tambo backend (Docker), plus 3 custom Python services: `argus-result-set-guard`, `argus-mcp-manager`, and the mongodb-mcp-server sidecar.
- **The user's MongoDB** is the data source. We never touch it directly — only through the MCP server, with the user's connection string.

### The 3 write-protection layers

- **mongodb-mcp-server** runs in read-only mode.
- **Onboarding** recommends a read-only database user.
- **argus-result-set-guard** blocks `$out` and `$merge` at the planner layer.

### The 5 LLM touchpoints

- **Planner:** Picks which insight modules to render, based on the sampled schema. (Gemini 3 Flash.)
- **Card schema resolver:** Maps an insight module's output to a Zod-typed card prop. (Deterministic; no LLM.)
- **Card renderer:** Emits the Zod-typed card descriptor. (Deterministic; no LLM.)
- **Chat agent:** Handles free-form user questions. Picks which card to render. (Gemini 3 Flash.)
- **MQL generator:** Translates a user question into an aggregation pipeline. (Gemini 3 Flash with the schema as context.)

### The data flow for a typical request

1. User types: "show me the count of users by country."
2. Tambo (on Cloud Run) receives the request. Asks Gemini: "given this user message, which card should I render?" Gemini says: "StatCard with country breakdown."
3. Tambo calls the `mongodb_aggregate` tool on the `argus-result-set-guard`, which validates the pipeline (no `$out`, no `$merge`, has `.limit()`).
4. The `argus-mcp-manager` looks up the tenant's subprocess, calls `mongodb_aggregate` on the mongodb-mcp-server, which queries the user's MongoDB.
5. The result flows back: MongoDB → mongodb-mcp-server → mcp_manager → result_set_guard → Tambo → Vercel → user.
6. The StatCard renders with the data.

**Total elapsed time: 1-2 seconds for the typical case, 200-500ms of subprocess startup on first request after a 5-minute idle period.**

## Potential Impact

Argus is for the **MongoDB developer who wants insights without learning the aggregation framework.** Today, the workflow is: read the docs, write a 50-line pipeline, run it, parse the result, build a chart. Argus compresses that into a chat message.

**Target user:** Solo developer or small team with a MongoDB Atlas cluster. Doesn't have a data analyst. Wants to know "what's happening with my data" without a data warehouse.

**Pricing model:** Open source, self-hosted, free. Cloud Run + MongoDB Atlas M0 = $0/month at low scale.

**Distribution:** GitHub + MongoDB community (Reddit, Slack, dev.to). Targeted at the MongoDB AI Hackathon 2026 audience.

**Wedge:** The 3 layers of write protection. Once you've used Argus on a real cluster, you can't go back to "let me just run this in mongosh."

## Known Limitations

Argus v1 ships with the following limitations. Each is a known issue with a planned v2 path.

- **No PII redaction.** v1 renders fields matching `/email|phone|ssn|pass|token|card|address|ip/i` as raw text. Recommended: connect with a sandbox cluster for the demo.
- **No API-level auth.** v1 has no per-user authentication. Recommended: deploy behind a Cloud Run gateway with an API key.
- **IP-restricted MongoDBs require Serverless VPC.** v1 uses Cloud Run's default egress. Production deployments should use Serverless VPC + Cloud NAT (see Appendix C).
- **No Atlas Performance Advisor.** Requires M10+ cluster. v1 uses `atlas-list-clusters` and `atlas-describe-cluster` (M0-compatible).
- **Anomaly detection is v1 of the algorithm.** Z-score on daily metrics. v2 will use seasonal decomposition (STL).
- **Attribution is first-touch only.** v2 will add Markov chains and Shapley values.
- **No change streams.** Dashboards are polled, not pushed. Refresh interval is 30s by default.
- **No write tools.** By design. The 3 layers of write protection are non-negotiable.

## Appendix C: Production deployment with IP-restricted MongoDBs

Argus v1 uses Cloud Run's default egress, which has dynamic IP addresses. If your MongoDB cluster has an IP allow-list, you'll need to route Cloud Run's egress through a static IP.

**Setup (30 minutes):**

```bash
# 1. Reserve a static IP
gcloud compute addresses create argus-egress-ip --region=us-central1

# 2. Create the VPC connector
gcloud compute networks vpc-access connectors create argus-connector \
  --region=us-central1 \
  --network=default \
  --range=10.8.0.0/28

# 3. Create the Cloud Router
gcloud compute routers create argus-router --network=default --region=us-central1

# 4. Create the Cloud NAT
gcloud compute routers nats create argus-nat \
  --router=argus-router \
  --region=us-central1 \
  --nat-external-ip-pool=argus-egress-ip
```

Then in Cloud Run, set `--vpc-connector=argus-connector --vpc-egress=private-ranges-only`. The static IP is shown with `gcloud compute addresses describe argus-egress-ip --region=us-central1`. Add this IP to your MongoDB Atlas Network Access list.

**Cost:** ~$30/month for the Serverless VPC connector. Scales with traffic.
